## 执行摘要

**要解决的问题。** p2pchain 目前只有命令行节点（`p2pchain node / wallet / init / printchain / verify / reset`）和一个内嵌的 Developer Console 网页。普通用户需要同时会用终端、口令文件、HTTP 接口才能挖矿和转账，门槛过高。本项目交付一个桌面客户端，把节点管理、挖矿、钱包、区块浏览和日志整合到一个窗口内，开箱即用。

**方案。** 采用 Python + PySide6 构建 GUI，通过本机 HTTP 控制接口（`127.0.0.1` 上的控制面，**v1.3：11 条端点**）驱动已有的 Go 节点二进制。GUI 以子进程方式托管本地节点（内嵌模式），也可连接局域网或云上的已有节点（远程模式，只读优先）。链上数据永远以节点返回为准，GUI 本地仅保存地址标签、交易备注等展示层数据。

**为什么不是 Rust。** Rust 的价值在节点本体（单二进制、内存安全、性能），不在桌面遥控器。用 Rust 重写 GUI 既要重学一套尚在演进的 GUI 生态（egui / iced / Slint），又容易诱发在 Rust 侧复刻签名或共识逻辑的冲动 — 一旦出现第二份共识实现，分叉风险远大于收益。团队已有 PySide6 实战经验（quiet-messenger 桌面端），GUI 本身是 I/O 密集型，Python 性能绰绰有余。结论：**GUI 用 Python + PySide6，节点继续用 Go，二者通过现有 RPC 解耦。**

**交付节奏。** 分四阶段：只读仪表盘与日志先行（零资金风险），挖矿面板其次，钱包转账最后（整条链路稳定后才碰钱），打包分发收尾。总周期约 5–7 周（单人）。

## 1 决策结论：为什么选 Python + PySide6

本章给出选型结论与不可动摇的架构约束。后续所有设计都服从这三条约束；任何与之冲突的实现提案直接否决，不进入评审。

### 1.1 结论

| 层面 | 选择 | 理由（一句话） |
|---|---|---|
| 桌面 GUI | **Python 3.11+ + PySide6 (Qt 6)** | 团队已有交付经验，Qt 是桌面端最成熟的跨平台方案，开发速度最快。 |
| 节点 / 共识 / 挖矿 / 钱包加密 | **保持 Go 实现，不动**（`p2pchain` 二进制） | 共识代码有且只能有一份实现；已有实现经过 P0-1 至 P0-6/P0-8 审计与修复验证。 |
| GUI 与节点通信 | **HTTP JSON 控制接口**（本机回环） | 节点已提供完整的控制面（**v1.3：端点 11 条**，原 13 条中的 `/mine`、`/console/mine` 已下线），无需新增 IPC 协议。 |
| 打包 | **PyInstaller** 单文件 + 平台节点二进制捆绑 | Windows / Linux / macOS 各打一份，内含对应平台的 `p2pchain`。 |

### 1.2 三条铁律（架构级约束）

> **铁律 1 — Python 侧零共识、零密码学复刻。** 不在 Python 中实现签名、地址派生、PoW 校验、难度计算、交易构造或 UTXO 选择。所有链上操作一律通过 Go 节点的 HTTP 接口完成。Python 里重写一遍签名逻辑，就是下一个共识分歧（分叉）的来源。GUI 需要展示难度、成熟度等派生量时，只展示节点已返回的字段（如 `/status` 的 `bits / difficulty`），不自行推导。

> **铁律 2 — 钱包口令只进内存，不落盘、不进日志、不进命令行。** 口令通过密码输入框获取，仅在调用节点时经内存传递给 Go 侧的口令文件机制或节点进程；用完立即清除引用。如实声明局限：Python 无法提供 Go `ZeroBytes` 级别的内存擦除保证（解释器对象复用与 GC 使擦除只能做到 best-effort），因此口令在 GUI 进程内的驻留时间必须最短，且 GUI 进程本身不得被当作长期托管口令的场所。长期运行的节点口令仍由 Go 侧的 `--wallet-password-file`（0600 文件）承担。

> **铁律 2 例外条款（v1.2 引入、v1.3 收紧条件 1，唯一且封闭的例外）。** 允许 GUI 提供「生成口令文件」便利功能（已实现，见 §7.1 补充），但**必须同时满足以下四条，缺一不可**：
>
> 1. **必须使用 CSPRNG，且熵不低于 32 字节（256 bits）。** 口令只能由 `secrets` 模块（或等价密码学安全随机源）生成，**禁止** `random` 等非密码学随机数。
>
>    **熵下限是硬指标，且以「字节（byte）」而非「字符（char）」计量** —— 这是本条最容易踩错的地方：
>
>    | 写法 | 字符数 | **实际熵** | 是否合规 |
>    |---|---|---|---|
>    | `secrets.token_hex(16)` | 32 hex 字符 | **16 字节 = 128 bits** | ❌ 看着「满足 32 字符」，实则只有一半熵 |
>    | `secrets.token_urlsafe(24)` | 32 base64 字符 | **24 字节 = 192 bits** | ❌ 同上，3/4 熵 |
>    | `secrets.token_hex(32)` | 64 hex 字符 | **32 字节 = 256 bits** | ✅ **本条要求的档位** |
>
>    **合规写法**：`secrets.token_hex(32)`，与 P0-4 的 AES-256-GCM 密钥强度对齐。
>    节点侧读取时做 `TrimSpace`，64 字符完全落在 `wallet.LoadPasswordFile` 的
>    `[12, 4096]` 区间内；口令永不显示，可读性不构成约束。
>
>    **同理适用于同源秘密**：控制接口 Bearer 令牌文件（`ensure_token_file`）属同一类
>    秘密，同样适用 32 字节熵下限（节点侧 `LoadTokenFile` 区间 `[16, 1024]`，64 字符合规）。
> 2. **直接以 0600 原子写入，不经任何旁路。** 写入过程不得经过剪贴板、不得在界面显示、不得记入日志或任何持久化（含设置文件与崩溃报告）；Unix 下权限位必须为 0600。
> 3. **仅限本地内嵌模式。** 该功能只服务于「节点就在本机」的场景；**远程模式下必须禁用**——远程场景中口令文件需传到服务器，一旦退化为「显示口令让用户复制」，即彻底破坏本铁律。远程节点的口令文件应由用户在服务器上自行创建。
> 4. **尽快释放内存中的口令字节。** 生成后应立即缩短口令明文在 Python 进程内的驻留时间；如实记录 Python 无法达到 Go `ZeroBytes` 级别的可靠擦除，此为**已知局限**，不视为违规。落地要求：生成用 `secrets` 以**局部导入 + 单行内联传递**完成，不赋值给任何长期存活的变量、不写入设置文件、不进崩溃日志。
>
> 本例外条款是对铁律 2 的**穷尽列举**。不得再以「便利」为由新增其他例外；任何新增例外必须走评审并写入本节。**验收口径**：以「四条同时成立」为通过条件，任一不满足即回退为纯指引（不生成）。

> **铁律 3 — 默认只连 127.0.0.1，远程连接必须显式确认。** 延续 P0-8 的 fail-closed 精神与 RPC 规范 §7 的安全边界：控制接口默认绑定回环地址才安全，7 条只读端点无鉴权、全体端点无 TLS。远程模式下 GUI 必须弹出明确风险提示，并强烈建议用户先建立 SSH 隧道再连接；禁止把远程地址静默持久化为默认连接。

### 1.3 什么时候才考虑 Rust

以下情形出现时再评估 Rust，且评估对象是节点本体而非 GUI：需要将节点做成极小体积的单二进制分发、需要极致的挖矿或网络吞吐优化、或要开发与链无关的高频工具。在当前「集挖矿、钱包、节点管理于一身的桌面端」目标下，Rust 属于过度投入：学习与生态成本数月起步，收益却落在 GUI 并不需要的性能维度上。

## 2 系统架构

### 2.1 总体结构

```text
┌──────────────────────────────────────────────────────────────┐
│ PySide6 GUI（Python 进程）                                    │
│  仪表盘 │ 挖矿面板 │ 钱包 │ 区块浏览器                       │
│  网络面板 │ 日志面板 │ 首次启动向导 │ 设置                    │
├──────────────────────────────────────────────────────────────┤
│ 连接与会话层                                                  │
│  节点进程启停与健康检查 · Bearer 令牌内存持有                 │
│  轮询调度（QTimer）· 超时与重试 · 错误码统一翻译              │
│ 本地存储（SQLite）：仅地址标签、交易备注、UI 偏好             │
└───────────────────────┬──────────────────────────────────────┘
                        │ HTTP 127.0.0.1:<rpc>（默认 6689，可配）
                        │ QNetworkAccessManager + QProcess
┌───────────────────────▼──────────────────────────────────────┐
│ Go 节点 p2pchain（二进制，子进程或远程进程）— 唯一真值        │
│  共识校验 · P2P 网络 · 挖矿引擎                              │
│  钱包加密（PBKDF2 + AES-256-GCM）· UTXO 集 · 区块存储        │
│  控制接口（11 端点，v1.3）                                    │
└──────────────────────────────────────────────────────────────┘
```

两个进程只通过回环 HTTP 通信，不共享内存，不通过文件直接读写链数据（离线命令除外，见 6.4）。

- **仪表盘**：高度 / 算力 / 对端 / 同步状态 / 余额概览，轮询 `/status`
- **挖矿面板**：启停、worker 数、已出块、算力曲线
- **钱包**：余额 / 转账 / 历史 / 地址簿
- **区块浏览器**：列表 / 搜索 / 交易详情
- **网络面板**：Peer 列表、入站/出站、封禁状态
- **日志面板**：实时滚动（`/logs` 尾部轮询）
- **首次启动向导**：数据目录、端口、口令文件引导

### 2.2 两种运行模式

| 模式 | 内嵌模式（默认） | 远程模式 |
|---|---|---|
| 节点来源 | GUI 用 `QProcess` 拉起随包分发的 `p2pchain node` 子进程 | 连接用户指定的已有节点（局域网 / 云服务器） |
| 数据目录 | 向导选择或默认目录，GUI 全权管理启停 | 节点自管，GUI 不碰其数据目录 |
| 适用人群 | 个人挖矿、本地测试、首次体验 | 多机部署、云节点监控、团队共享节点 |
| 权限 | 全功能（含启停挖矿、转账、停节点） | 默认只读；写操作需用户显式解锁并确认风险（见第 7 章） |
| 关闭行为 | GUI 退出时优雅停止子节点（先停挖、再停节点） | GUI 退出不影响远程节点 |

### 2.3 进程与线程模型

- **主线程** 只做 UI 渲染与事件处理，绝不阻塞等待网络。
- **网络请求** 统一走 `QNetworkAccessManager` 异步调用，配合 `QTimer` 做分级轮询：`/status` 每 2 秒、`/logs` 每 3 秒、余额在高度变化时刷新。页面不可见时自动降频。
- **节点子进程** 的 stdout/stderr 由 `QProcess` 管道捕获，既写入日志面板也落盘到 `<datadir>/logs/`（与此前 Windows 测试方案一致：落盘文件才是完整历史，`/logs` 环形缓冲只适合即时查看）。
- **崩溃恢复**：子节点异常退出时 GUI 不自动无限重启，而是提示退出码与最近日志，由用户决定重启（吸取云上无 systemd 时手动拉起的运维经验）。

> **实现补充（v1.1）**：实际实现未用 `QNetworkAccessManager`，而是**标准库 `urllib` + `QThread`**（`widgets.AsyncMixin.run_async` 把阻塞调用丢到工作线程，结果经信号回主线程）。选型理由：零第三方依赖、便于 PyInstaller 打包；线程模型与本章「主线程不阻塞」的约束一致。`NodeProcess` 亦为 `QProcess` 优先、`subprocess.Popen` 自动回退。详见附录 C.3。

## 3 技术选型对比（Python + PySide6 vs Rust）

本章把第 1 章的结论展开为可核查的对比，避免选型停留在偏好层面。对比维度按对本项目的影响排序。

| 维度 | Python + PySide6 | Rust（egui / iced / Slint / Tauri 等） |
|---|---|---|
| **团队上手成本** | **已有交付经验**：quiet-messenger 桌面端即 PySide6，信号槽、模型视图、打包坑均已踩过，可直接复用经验与代码模式。 | 需从零学习语言（所有权、生命周期）与 GUI 框架；团队无 Rust 桌面交付记录。 |
| **GUI 生态成熟度** | **Qt 6 是最成熟的跨平台桌面方案**：控件完整、无障碍、打印、高 DPI、系统托盘均有现成支持；文档与社区规模最大。 | egui/iced 适合工具型界面但控件与无障碍仍在演进；Slint/Tauri 各有取舍，选型本身就需要额外评估周期。 |
| **与 Go 节点的集成** | **HTTP 客户端开箱即用**（`QNetworkAccessManager` / `httpx`），JSON 处理零摩擦；进程托管用 `QProcess` 一站完成。 | 同样走 HTTP 时无额外优势；若试图用 FFI 直接链接 Go 库，反而制造构建与 ABI 复杂度。 |
| **共识安全风险** | **天然隔离**：Python 侧没有高性能密码学库的诱惑，团队共识是「只调接口」，不易滑向复刻实现。 | **风险更高**：Rust 的高性能形象容易诱发「顺手在 Rust 里验个签、算个难度」的第二实现冲动，一旦出现即为分叉隐患（铁律 1）。 |
| **性能** | GUI 为 I/O 密集型（轮询、渲染表格），Python 完全够用；挖矿算力在 Go 侧，与 GUI 语言无关。 | CPU 密集型场景更强，但本 GUI 没有此类热点；为不需要的性能付学习成本不划算。 |
| **打包与分发** | PyInstaller 成熟稳定；包体积较大（约 80–150 MB，含 Qt 与节点二进制），可接受。 | 单二进制体积小，但 Qt 绑定（cxx-qt 等）构建链更复杂，CI 成本更高。 |
| **迭代速度** | **改界面即时生效**，适合先出只读版快速验证再逐步加功能（第 10 章路线图）。 | 编译与借用检查使 UI 快速试错更慢。 |

> **选型口诀：** GUI 拼的是开发速度与生态成熟度，节点拼的才是性能与安全。前者选 Python+PySide6，后者已经选了 Go。不要用节点的标准去选 GUI，也不要用 GUI 的语言去重写节点。

## 4 功能模块设计

共七个模块。排序即交付顺序：只读模块先行，资金相关模块最后。每个模块标注所依赖的 RPC 端点（端点定义见第 5 章，编号如 [S1]）。

### 4.1 仪表盘（只读，最先交付）

- 数据来源：`GET /status` [S1] 每 2 秒轮询。展示链高度、链尾哈希（截断显示、可复制）、内存池大小、对端数、钱包地址。
- 挖矿状态必须用 `mining_state` 而非布尔 `mining` 判断真实语义（STOPPED / STARTING / RUNNING / STALLED / FAILED / STOPPING），异常时展示 `mining_reason`。同时展示 `pow_attempts`、`accepted_blocks / rejected_blocks` 与下一块的 `bits / difficulty`。
- 余额卡片调用 `GET /balance` [S2]，区分可花费（spendable）与含未成熟的总额（total），避免用户误判 coinbase 未成熟为「丢币」。

### 4.2 挖矿面板

- 启动/停止持续挖矿：`POST /mine/start` [M3]、`POST /mine/stop` [M4]（均需 Bearer）。停止挖矿绝不停止节点，UI 文案必须明确区分「停挖」与「停节点」。
- 按需出块（测试网）：`POST /mine` [M2]，数量上限 1000，界面做范围校验并提示该操作与持续挖矿互斥（节点在持续挖矿时会拒绝按需出块）。
- worker 数与最大块数对应节点启动参数 `-miners / -maxblocks`，在内嵌模式的启动配置中设置；运行中不可热改，改后需重启节点，UI 需明示。
- 算力曲线：由 `pow_attempts` 的差分计算（次/秒），本地采样绘图，不回传节点。

### 4.3 钱包（资金功能，最后交付）

- 余额与 UTXO：`GET /balance` [S2]、`GET /utxos` [S3]。UTXO 列表展示金额、高度、是否 coinbase、是否成熟。
- 转账：`POST /send` [M1]（Bearer 必需）。表单含收款地址、金额、手续费；提交前做本地地址格式预检（仅格式，不做签名学校验）、余额充足性预检与二次确认弹窗（地址、金额、手续费三项复述）。
- 交易历史：由 `GET /blocks` [S5] 分页拉取后本地过滤本钱包地址相关交易生成（节点无专用历史端点，见 5.3 的能力边界）。本地仅缓存展示结果，不作为账本真值。
- 地址簿：本地 SQLite 保存标签（见第 8 章）；节点钱包地址本身来自 `/status` 的 `address` 字段，GUI 不生成新地址（生成地址属于节点钱包职责）。

### 4.4 区块浏览器（只读）

- 列表：`GET /blocks?from=&count=` [S5]，单页上限 100。采用「最新在前」的产品语义：请求时以链尾高度反推 `from`，注意节点返回为高度升序（链序），GUI 侧倒序展示。
- 详情：`GET /block` [S4] 按 `height=` 或 `hash=` 二选一（互斥，同时传参节点返回 400）。展示区块头、交易列表、难度、大小与共识纪元（`consensus_era`）。
- 诚实空态：普通交易的手续费在节点侧因缺少历史输出索引而省略（`fee` 字段缺失），GUI 必须显示「—」而非伪造的 0。

### 4.5 网络面板（只读为主）

- 对端列表来自 `/status` 的 `peers` 数组，做连通性与数量展示。
- P0-5 的记分/封禁状态目前没有专用 RPC 端点，GUI 第一版仅展示对端列表与连接数，不虚构封禁可视化；待节点后续暴露端点再接入（记入非目标，见第 11 章）。

### 4.6 日志面板

- `GET /logs?tail=` [S6] 轮询（默认 100，上限 500，超限节点静默裁剪）。无日志来源时节点返回空数组，GUI 显示诚实空态，不编造内容。
- 内嵌模式同时把子进程 stdout 落盘，面板提供「打开完整日志文件」入口，弥补环形缓冲只有最近 500 条的不足（与 Windows 全流程测试的落盘方案一致）。
- 支持按级别筛选（本地字符串过滤）、暂停滚动、导出当前视图。

### 4.7 首次启动向导与设置

- 向导四步：选择模式（内嵌/远程）→ 数据目录与端口（内嵌时）→ 口令文件引导（仅指引用户在本地创建 0600 口令文件，GUI 不生成、不读取口令内容）→ 完成并启动。
- 设置页管理：RPC 地址、轮询间隔、本地数据库路径、节点启动参数模板。所有写操作参数修改后需重启节点生效，界面明示。

> **实现补充（v1.1）**：实际交付**没有独立的首启向导**，改为**「设置」页 + 「节点控制」页**承担等价职责（连接、项目路径、二进制、启动参数、token/口令文件）。启动参数模板以内嵌表单呈现，并做**启动前置校验**（`LaunchSpec.problems()`：可执行文件/数据目录/口令文件/非回环四项）。另有一处与铁律 2 边界的偏差已收口：**GUI 提供「生成口令文件」按钮**（`config.ensure_wallet_password_file`，CSPRNG 生成 + 0600 原子写入），即 GUI 会**生成**随机口令并落盘为文件，但**从不读取、显示或持久化口令明文**，也不进日志。该功能已按 **§1.2「铁律 2 例外条款」** 收口（四条硬性条件，含**仅本地模式**——远程模式下该入口已禁用）。

### 5.3 认证模型（与规范 §2 核对，GUI 必须遵守）

| 规则 | 内容 |
|---|---|
| Bearer 传递方式 | 请求头 `Authorization: Bearer <token>`；节点侧用 `crypto/subtle.ConstantTimeCompare` 常量时间比较，防时序侧信道。 |
| fail-closed（最重要） | 节点未配置令牌（`expected == ""`）时，变更端点**一律 401**，不放行。GUI 不得把 401 解读为「无令牌可用裸奔」，必须引导用户正确配置令牌文件。 |
| 失败延迟 | 认证失败有固定延迟（默认 500 ms，防爆破）。GUI 对 401 不做快速重试，避免叠加延迟与无意义请求。 |
| 令牌约束 | 长度 16–1024；非 Windows 下令牌文件须 0600，过宽则节点启动报错。节点参数 `-auth-token-file`（默认 `secrets/control-token`）。只传路径，不进命令行/环境变量/日志；GUI 读入后仅内存持有。 |
| 只读端点免鉴权的前提 | S1–S6、P1 无鉴权是**有意设计**，安全完全依赖回环绑定；绑到非回环即无保护暴露。GUI 远程模式按第 7 章提示风险。 |

### 5.4 核验发现：1 处规范滞后（需修订规范，不改实现）

> **发现 D-1：`/console/mine` 的鉴权方式，规范文本已滞后于实现。**
>
> 规范 §2.2 与 §3 将 `/console/mine` 描述为「同源闸门」（校验 `Sec-Fetch-Site / Origin`，非同源返回 403），§4.8 沿用同一说法。但当前实现（`server.go` 331–336 行，`PHASE RPC-CONTROL-PLANE-AUTH-HARDENING-1`）已将该端点改为与 `/mine` 完全一致的 **Bearer 认证**（`requireAuth`），并在注释中明确废止了同源闸门（原同源路径被认定为「无 Bearer 即可出块」的未授权变更路径）。
>
> **处理原则：** 按仓库治理规则「最高真值为可执行实现 + 可重复测试」，应以实现为准，修订规范 §2.2、§3、§4.8 三处描述。在规范修订前，GUI 一律按 Bearer 对待 `/console/mine`（本设计本就不调用该端点，影响面为零）。此项记入待办，不阻塞 GUI 开发。

其余 12 条端点的方法、参数、响应与错误语义，规范与实现逐条一致（含 `/mine/stop` 的幂等与 FAILED 保留、`/stop` 无钩子返回 501、`/blocks` 的升序与 `at_tip` 语义、`/logs` 的诚实空态等）。规范 §8 登记的旧文档漂移（「6 个端点 / 无鉴权」）与本次核验结论一致，旧说法已作废。

### 5.5 错误码约定（与规范 §6 一致，GUI 统一翻译）

| 状态码 | 出现场景 | GUI 处理 |
|---|---|---|
| 400 | 参数缺失/非法、请求体解析失败、地址或哈希非法、分页越界、`height` 与 `hash` 同传 | 展示节点返回的具体原因（错误体含实际值），定位到表单字段；不自动重试。 |
| 401 | 变更端点 Bearer 未通过（含未配置令牌的 fail-closed） | 提示检查令牌文件配置；不快速重试（有 500 ms 防爆破延迟）。 |
| 404 | 按哈希查区块未命中；控制台路径不匹配 | 浏览器显示「未找到」空态。 |
| 405 | 方法不符（附 `Allow` 头） | 视为客户端 bug，记录日志并提示升级。 |
| 409 | `/mine/start` 状态冲突（已在跑 / FAILED / STOPPING） | 展示响应中的 `state`，引导用户先处理当前状态。 |
| 500 | 节点侧状态/余额/UTXO 获取失败 | 提示节点异常，展示原因，允许手动刷新。 |
| 501 | `/stop` 无停止钩子（节点未启用远程停止） | 提示该节点不支持远程停止，需在节点侧手动停止。 |

### 5.6 变更端点幂等性（决定重试策略）

| 端点 | 幂等 | 副作用与 GUI 策略 |
|---|---|---|
| `/send` [M1] | 否 | 构造交易、入池、广播。**禁止自动重试**；超时后先查状态再由用户决定，避免重复转账。 |
| `/mine` [M2]、`/console/mine` [M5] | 否 | 同步挖 N 块。超时不自动重试。 |
| `/mine/start` [M3] | 否（冲突 409） | 启动持续挖矿。收到 409 时读取当前状态展示，不盲目重试。 |
| `/mine/stop` [M4] | **是** | 可安全重试；返回的是受理状态（STOPPING），最终 STOPPED 以 `/status` 为准，GUI 需轮询确认。 |
| `/stop` [M6] | 否 | 停止节点。发出后连接必然断开，GUI 按「节点已停止」处理，不判为错误。 |

```text
GUI 启动
  └─ 向导/设置读取：datadir、listen、rpc、seed、mine/miners/maxblocks、口令文件路径
  └─ QProcess 启动：p2pchain node -datadir <d> -listen <a> -rpc 127.0.0.1:<p>
                    -wallet-password-file <f> [-mine -miners N -maxblocks M] [-seed <s>]
       ├─ stdout/stderr → 日志面板 + 落盘 <datadir>/logs/node.log
       ├─ 就绪检测：轮询 GET /status 直到 200（超时 30 秒判失败，展示日志尾部）
       └─ 运行中：每 2 秒 GET /status 刷新仪表盘；进程退出事件 → 标记离线并提示
  └─ GUI 退出（或用户点「停止节点」）
       ├─ 若在挖矿：POST /mine/stop → 轮询 /status 直到 mining_state=STOPPED
       ├─ POST /stop（Bearer）→ 节点优雅释放数据目录锁后退出
       └─ 等待 QProcess 结束（超时 10 秒后提示，不强杀正在写盘的节点）
```

要点：停节点顺序固定为「先停挖、后停节点」，与 Go 侧主流程的关闭次序（先 `minerStop`、再由关闭链释放存储与锁）保持一致，避免关停与在途 `AddBlock` 并发。同一数据目录一次只能由一个节点进程使用，若节点报数据目录被占用，GUI 直接展示节点给出的可执行提示，不自动删锁文件。

### 6.2 挖矿控制流程

```text
用户点「开始挖矿」
  └─ POST /mine/start（Bearer）
       ├─ 200 → 状态置为节点返回的 state，后续以 /status 的 mining_state 为准刷新
       ├─ 409 → 读取 error + state（已在跑 / FAILED / STOPPING），展示并引导处理，不重试
       └─ 401 → 提示令牌配置问题
用户点「停止挖矿」
  └─ POST /mine/stop（Bearer，可安全重试）
       └─ 返回 STOPPING 仅为受理；轮询 /status 直到 STOPPED 再置灰按钮
状态展示规则：
  RUNNING 才显示「挖矿中」与算力曲线；STALLED 显示原因（如补贴耗尽无手续费交易）；
  FAILED 保持失败证据展示，不自动清除，需用户确认后处理。
```

### 6.3 转账流程（资金功能，Phase 3）

```text
填写表单（收款地址、金额、手续费）
  └─ 本地预检：地址格式（Base58Check 形态）→ 余额充足性（GET /balance 的 spendable）
  └─ 二次确认弹窗：复述地址、金额、手续费、预计剩余（禁止只显示金额）
  └─ POST /send（Bearer）— 非幂等，单次发送，绝不自动重试
       ├─ 200 → 展示 txid，提供「在浏览器中查看」与复制
       ├─ 400 → 展示节点具体原因（地址非法/参数非法），回到表单
       ├─ 401 → 令牌问题提示
       └─ 超时/断开 → 不重发；提示用户到浏览器核对交易是否已入池，再决定下一步
```

金额单位以节点接口的整数单位为准（`amount / fee` 均为 `uint64`），GUI 负责单位换算展示但提交时必须回算为整数并让用户在确认弹窗中核对整数值，杜绝浮点误差进入链上金额。

### 6.4 轮询与离线命令边界

- **在线数据一律走 RPC。** GUI 不直接读 `blocks.dat`，不解析链文件。
- **离线命令仅作高级工具入口**：设置页提供「离线校验」（调用 `p2pchain verify -datadir <d>`，只读回放）与「打印链」（`printchain`）的只读入口；`reset` 为破坏性命令（删链/钱包/锁），必须二次确认且默认隐藏，不在主界面露出。
- 钱包的离线查看/创建（`p2pchain wallet`）同理只作高级入口；日常余额与地址展示走 RPC，不触碰钱包文件。

## 7 安全设计

安全模型与节点的既有修复（P0-4 钱包加密、P0-5 Eclipse 缓解、P0-8 回环约束）对齐。GUI 不创造新的密钥、不扩大暴露面；它的职责是把既有安全机制正确地用起来，并把风险如实呈现给用户。

### 7.1 密钥与令牌的归属（谁管什么）

| 秘密 | 归属与存储 | GUI 的处理 |
|---|---|---|
| 钱包私钥 | Go 节点内；落盘为 v2 加密信封（PBKDF2-HMAC-SHA256 60 万轮 + AES-256-GCM），位于 `<datadir>/secrets/wallet.json` | **永不接触。** 不读取钱包文件，不要求用户在 GUI 中导入私钥。 |
| 钱包口令 | 用户本地的口令文件（0600），节点以 `--wallet-password-file` 读取；唯一来源，不进命令行/日志 | 只在向导中**指引**用户创建口令文件并做路径配置；不在 GUI 中生成、显示或持久化口令明文（铁律 2）。 |
| 控制接口 Bearer 令牌 | 令牌文件（默认 `secrets/control-token`，0600），节点以 `-auth-token-file` 读取 | 从同一令牌文件读入后仅内存持有，附在变更请求头中；不写入 GUI 的设置文件或日志，界面只显示「已配置/未配置」。 |
| 本地标签数据 | GUI 的 SQLite（地址标签、交易备注） | 非秘密，可落盘；与链数据严格分离，删之不损链。 |

> **实现补充（v1.1 / v1.2 收口）**：实际 GUI 的「钱包口令文件」一栏提供 **选择** 与 **生成** 两个按钮；「生成」会写入一个强随机口令到用户指定路径。即：GUI 会**创建**口令文件，但**绝不读取、显示、记录或持久化其内容**——口令始终只存在于该 0600 文件与节点进程内，GUI 进程不持有明文。**该便利功能已按 §1.2「铁律 2 例外条款」收口（v1.2 引入、v1.3 收紧条件 1）**：保留按钮，但受四条硬性条件约束——① CSPRNG（`secrets`）**且熵 ≥32 字节 / 256 bits**：v1.2 采用 `secrets.token_urlsafe(24)`（32 字符 / **仅 192 bits**），**v1.3 起升级为 `secrets.token_hex(32)`（64 hex 字符 / **256 bits**）**，与 P0-4 的 AES-256-GCM 对齐（详见 §1.2 条件 1 的字节 vs 字符对照表）；② **0600 原子写入**（同目录临时文件 `O_CREAT|O_EXCL,0600` + `os.replace`，消除权限窗口）；③ **仅本地内嵌模式**（远程模式下该入口已禁用，避免退化为「显示口令供复制」）；④ 生成后尽快释放明文引用（Python 无法达 Go `ZeroBytes` 级擦除，属已知局限）。界面提示「口令文件丢失即钱包不可恢复，请异地备份」。另：「本地标签数据」一行所述 SQLite 实际未实现（见 8.2 补充）。

### 7.2 连接安全分级

| 场景 | 默认权限 | 要求 |
|---|---|---|
| 本机回环（127.0.0.1） | 全功能 | 正常使用；仍需 Bearer 才能执行变更操作（节点 fail-closed 不因回环而豁免）。 |
| 局域网远程节点 | 只读 | 连接时弹出风险提示（只读端点无鉴权、无 TLS 明文）；写操作需用户显式解锁并再次确认。 |
| 公网 / 云服务器 | 只读且强提示 | 强烈建议先建 SSH 隧道再连回环端口；禁止引导用户把 RPC 直接绑公网。GUI 不提供「一键公网连接」。 |

> **实现补充（v1.2）· 闸门已实现。** 本表「远程 → 只读 + 显式解锁」已落地为代码：`AppContext.require_write()` 在全部 mutation 入口前统一把关。规则：**本地回环（含 SSH 隧道端点）放行**；**远程默认锁定**，首次写操作弹出风险确认（默认按钮为「取消」），确认后**仅本次会话**解锁；**切换 RPC 地址即自动重新锁定**（fail-closed）。工具栏与状态栏均有可见指示（「写入：本地 / 远程只读·已锁定 / 远程已解锁 ⚠」）。回归测试见附录 C.5 第 12 节（11 项，全绿）。至此 §7.2 的纵深防御第二道由「设计意图」变为「可执行实现」。
>
> **v1.3 增补· 三项加固（本版新增要求）。** v1.2 的闸门存在**安全语义缺口**，本版补齐，三者均为通过条件：
>
> 1. **mutation 控件必须置灰禁用（不只是动作时拦截）。** 远程且锁定态下，转账/挖矿启停/
>    停节点等写入类控件应 `setEnabled(False)` 并给出可发现的原因提示。
>    **理由**：只在点击时拦截属于 UX 不诚实——用户应当**一眼看出**当前是「远程只读」，
>    而不是「点了才知道被拦」。拦截（`require_write`）仍保留，作为纵深防御的**第二层**。
> 2. **连接断开必须自动重锁（本版最要紧的修复）。** v1.2 只在「切换 RPC 地址」时重锁，
>    但**断开后重连同一 RPC 会保持解锁态** —— 这实质绕过了「仅本会话」的承诺。
>    要求：轮询检测到连接丢失（连续失败 / 进入离线态）即 `set_remote_unlocked(False)`，
>    恢复连接后如需写入须**重新显式解锁**。
> 3. **解锁动作必须记本地操作日志（审计）。** 每次解锁（含工具栏开关与写入拦截弹窗两条
>    路径）向 GUI 本地操作日志追加一条记录：时间、目标 RPC 地址、来源（工具栏/写入拦截）。
>    **不记录令牌或口令本身**。理由：无审计即无问责——远程写入是高后果动作。
>
> **v1.3 同步修正**：随 `ON-DEMAND-MINING-REMOVAL-1`（按需出块全量下线，`POST /mine`
> 与 `POST /console/mine` 已移除、恒 404），受闸门约束的 mutation 入口由 **5 个修正为 4 个**
> （`/mine/start`、`/mine/stop`、`/send`、`/stop`）。
>
> **判定口径（须知晓）**：闸门以「RPC 地址是否回环」为界。经 **SSH 隧道**连接时本地地址是 `127.0.0.1`，按本表归入「本机回环」→ **放行**。这是**有意为之**：隧道由 SSH 提供加密与主机认证，正是本表推荐的安全路径；闸门要防的是「无 TLS 直连远程 RPC」。若运维上希望连隧道也强制解锁（例如云上为共享/生产节点），可后续增加「始终要求解锁」开关——已记入附录 C.6。

### 7.3 GUI 自身的安全清单

- 日志与错误提示中脱敏：不打印令牌、口令、完整请求头；崩溃报告默认不含连接凭据。
- 转账确认弹窗防误触：金额与地址用等宽字体复述，地址支持逐字核对与从地址簿选择，减少粘贴劫持风险（仍提示用户核对首尾字符）。
- 子进程启动参数以参数数组传递（`QProcess` 参数列表），不拼接 shell 字符串，杜绝命令注入。
- 随包节点二进制在打包时记录 SHA256 并在发布说明中公布，版本与 GUI 版本绑定，避免混用未知二进制。
- 不自动更新、不静默联网：除用户主动连接的节点外，GUI 无其他网络外发。

> **与 P0 系列修复的关系：** P0-4 使静态私钥不再明文落盘，P0-5 使节点抗入站挤占与地址投毒，P0-8 约束了 RPC 的回环暴露。Desktop 若绕过口令文件、把 RPC 绑到公网、或在 Python 里复刻签名，等于把这三项修复的收益一次性清零。第 1 章铁律正是为此而设。

## 8 数据与状态管理

### 8.1 真值划分（最重要的边界）

| 数据 | 真值所在 | GUI 行为 |
|---|---|---|
| 链高度、区块、交易、UTXO、余额 | Go 节点（RPC 实时返回） | 只读展示与轮询刷新；不建本地账本，不做增量同步推导。 |
| 挖矿状态与算力 | Go 节点（`/status` 语义字段） | 以 `mining_state` 为准；算力曲线为本地采样派生展示，不回写。 |
| 钱包地址、私钥、口令 | Go 节点与用户口令文件 | 地址只读展示；私钥与口令永不进入 GUI 持久层（见 7.1）。 |
| 地址标签、交易备注、UI 偏好、远程连接历史（不含凭据） | GUI 本地 SQLite | 可自由增删改；丢失仅影响体验，不影响链上资产。 |

### 8.2 本地 SQLite 结构（仅展示层）

```sql
address_labels(address TEXT PRIMARY KEY, label TEXT, created_at INTEGER)
tx_notes(txid TEXT PRIMARY KEY, note TEXT, updated_at INTEGER)
ui_prefs(key TEXT PRIMARY KEY, value TEXT)          -- 轮询间隔、窗口布局等
connections(name TEXT, host TEXT, rpc_port INTEGER, readonly INTEGER)  -- 不存令牌
```

数据库位于 GUI 的应用数据目录，与节点 `datadir` 分离存放。禁止把链数据、钱包文件或令牌写入此库。

> **实现补充（v1.1）**：实际**未使用 SQLite**，改为单文件 JSON `%APPDATA%/P2PChainStudio/settings.json`（`config.Settings`，dataclass ↔ JSON 往返，原子写 `.tmp`→`replace`）。因此上表的 `address_labels / tx_notes / connections` 三张表**尚未实现**（地址簿、交易备注、远程连接历史为未落地项，见附录 C.6）；`ui_prefs` 的等价内容（`rpc_addr / refresh_ms / log_tail / theme / auto_refresh` 等）已随 JSON 持久化。与 `datadir` 分离存放的原则**保持不变**。

### 8.3 刷新与一致性策略

- `/status` 2 秒轮询驱动全局状态（高度变化时联动刷新余额与区块列表首页）。
- 页面切换时按需拉取（浏览器分页、UTXO、日志），不做全量预载。
- 所有写操作后不做乐观更新：以节点返回与下一轮 `/status` 为准确认最终状态（尤其 `/mine/stop` 的 STOPPING → STOPPED）。
- 断线时保留最后已知状态并明确标记「离线/数据可能过期」，不拿旧数据冒充实时数据。

## 11 风险、限制与非目标

### 11.1 已知限制（如实声明，不粉饰）

- **无 TLS、无 SPV**：控制接口为本机明文 HTTP，所有节点均为全节点（与项目既有限制声明一致）。远程使用必须依赖回环绑定或 SSH 隧道，GUI 不改变这一安全边界。
- **Python 内存擦除局限**：口令在 GUI 进程内只能做到 best-effort 清除，无法达到 Go 侧 `ZeroBytes` 的保证。因此长期口令托管仍走节点口令文件，GUI 不做口令保险箱。
- **日志完整历史依赖落盘文件**：`/logs` 仅最近 500 条（环形缓冲）。完整审计需读落盘日志，内嵌模式已自动落盘，远程模式则以节点侧文件为准。
- **普通交易手续费不可见**：节点因缺少历史输出索引而省略普通交易的 `fee`，GUI 诚实显示缺失，不推导、不伪造。
- **地址与曲线生态**：项目使用 P-256 + SHA256 截断的自定义地址（非比特币 secp256k1/RIPEMD160），GUI 不做跨链地址兼容或导入导出。

### 11.2 明确非目标（本版本不做）

- 不在 Python（或任何第二语言）中复刻签名、地址派生、PoW 或共识校验。
- 不做轻节点/SPV、不做多钱包管理、不做私钥导入导出与助记词。
- 不做 P0-5 封禁状态可视化（节点尚无对应 RPC 端点），不做交易广播策略配置。
- 不做自动更新与远程命令下发；不把 RPC 暴露到公网的产品化引导。

### 11.3 主要风险与缓解

| 风险 | 缓解 |
|---|---|
| 转账重复提交导致重复转账 | `/send` 非幂等：单次发送、禁止自动重试、超时先核对再决策（6.3）。 |
| 用户把 RPC 绑公网导致只读端点裸奔 | 默认回环、远程强提示、建议 SSH 隧道（7.2）；向导不提供公网绑定选项。 |
| GUI 与节点版本不匹配导致字段误读 | 版本绑定发布、启动时校验节点版本、未知字段容错展示（8.3、9）。 |
| 规范与实现再次漂移 | 以实现为真值并回修订规范（已发现的 D-1 即按此处理）；GUI 合同测试用假节点锁定端点语义。 |

## 附录 D 连接腾讯云节点（SSH 隧道）速查

> 云节点 A 的控制接口只监听其自身回环 `127.0.0.1:16689`，公网不可达。远程连接须先建 SSH 隧道把远端 `16689` 映射到本地 `16689`，再以 `127.0.0.1:16689` + token 连接。此即正文 §7.2「公网/云 → 先建 SSH 隧道」的落地方式。

### D.1 一键连接（推荐）

```bash
gui/connect-cloud.sh            # 仅维持隧道（前台常驻，断线 5s 自动重连）
gui/connect-cloud.sh --verify   # 建隧道 + 自检（/status + 带 token 的 /mine/start）
gui/connect-cloud.sh --gui      # 建隧道 + 自检 + 拉起本地 GUI
```

脚本行为：① 本地无 token 则 `scp` 拉取 `control-token` 到 `~/p2pchain-cloud/`；② 以 `ExitOnForwardFailure` + keepalive 建隧道并自动重连；③ 可选自检与拉起 GUI。可覆盖环境变量：`CLOUD_HOST` `CLOUD_SSH_PORT` `REMOTE_RPC_PORT` `LOCAL_RPC_PORT` `SSH_USER`。

### D.2 手动等价命令

```bash
# 建隧道（-N 不执行远端命令；前台常驻，断线由外层脚本/任务重连）
ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 \
    -L 16689:127.0.0.1:16689 -p 2222 root@111.229.225.123

# 只读端点（无需 token）
curl -s --noproxy '*' http://127.0.0.1:16689/status

# mutation 端点（需 Bearer Token）
curl -s --noproxy '*' -X POST \
    -H "Authorization: Bearer $(tr -d '\r\n' < ~/p2pchain-cloud/control-token)" \
    http://127.0.0.1:16689/mine/start
```

### D.3 两个必须知道的坑

1. **代理陷阱**：本机若设了 `HTTP_PROXY`（且 `no_proxy` 为空），stdlib `urllib` 会把 `127.0.0.1` 请求也交给代理，表现为 `upstream connect failed …(os error 10061)` 或 **HTTP 502**。用 `curl` 复现须加 `--noproxy '*'`；**GUI 已内置回环绕过**（`api.py._is_loopback_base`），无需额外配置。
2. **隧道进程存活**：`ssh -f -N` 的 fork 子进程在部分沙箱/终端会在命令返回后被回收（netstat 一度 LISTENING 随即 connection refused）。应以前台常驻或托管后台任务方式运行（`connect-cloud.sh` 即前台监管 + 自动重连）。

### D.4 在 GUI 中持久化云端配置

「设置」页把 `rpc_addr` 填 `127.0.0.1:16689`、`token_file` 指向本地 `control-token`，保存后每次启动即连云端；也可用 `P2PChainStudio.exe --rpc 127.0.0.1:16689 --token-file <path>` 临时覆盖。

> **当前拓扑**：A = seed（`16688`/`16689`），B、C 为从节点。持续挖矿由 A 的 `POST /mine/start` 驱动，重复调用返回 **409 `挖矿已在运行`**（幂等语义）。节点无 systemd，手动以 `nohup ./bin/p2pchain <args> >> logs/<log> 2>&1 &` 拉起。
