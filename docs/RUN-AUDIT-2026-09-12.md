§2 — REMEDIATION DESIGN  
\-----------------------  
实现最小、明确的释放路径保证：

1. 锁释放必须注册在最外层作用域的 defer 中（cmd/main 层级），  
   不得只存在于中间 shutdown 步骤里。  
   要求：任意路径退出（含 panic）都执行 release。
2. release 必须幂等：重复调用不得报错、不得误删他人重新获取的锁。  
   实现方式：release 内部校验 lock 文件内容中的 pid 等于本进程 pid  
   后才执行删除；不匹配则静默跳过（记录日志）。
3. SIGINT / SIGTERM 必须路由进与正常 shutdown 相同的 graceful 链，  
   不得为信号单独写一套释放逻辑。
4. lock 内容容错：node.lock 存在但内容为空、缺少字段或无法解析时，  
   启动拒绝行为不变（DATADIR_LOCKED），但不得 panic、不得误报其他错误类型。
5. CLI 引导文案：DATADIR_LOCKED 的用户级错误输出末尾追加固定提示：  
   "If no other node process is running, remove <datadir>/node.lock manually and restart."  
   要求：

- 仅作为提示追加，不改变错误类型与退出码语义
- 提示中的路径为实际 datadir 绝对路径
- 不得暗示程序会自动处理残留 lock

§4 — LOCK LIFECYCLE  
\--------------------  
显式顺序：  
acquire node.lock  
↓  
initialize node  
↓  
open storage  
↓  
start runtime  
↓  
（任意点失败或收到退出信号）  
↓  
stop runtime（如已启动）  
↓  
close storage（如已打开）  
↓  
release node.lock（最外层 defer 保证）  
要求：

- release 在所有路径上恰好执行一次（幂等是为防御，不是许可重复调用）
- release 之后进程才允许退出

§5 — CRASH / STALE LOCK POLICY  
\-------------------------------  
本阶段维持 P2.1 政策，不得放松：

- 禁止 lock exists → PID not running → 自动删除 → 继续启动
- 异常残留 lock 不得被静默覆盖（release 的 pid 校验是防御手段，  
  不得被用作"检测后自动删除"的通道）
- 为未来 stale-lock recovery 保留扩展点：  
  在 docs/design/stale-lock-options.md 中记录两个候选方案的对比  
  （pid liveness check vs OS advisory lock），仅记录结论与风险，  
  不得实现。
- 如需平台相关能力才能满足上述要求，必须先 STOP 并报告设计差异。

§6 — TESTS  
\-----------  
新增测试必须覆盖至少：  
Test 1 — SIGTERM releases lock  
启动真实 node 子进程 → 等待 ready → 发送 SIGTERM →  
等待退出 → 断言 node.lock 已删除 → 断言同 datadir 可重新 acquire。  
必须 PASS。

Test 2 — SIGINT releases lock  
同 Test 1，信号换为 SIGINT。必须 PASS。

Test 3 — 全部初始化失败点均释放锁（table-driven）  
对调用链上每个可注入失败的阶段（init / open storage / start runtime）  
分别注入失败：  
acquire → 该阶段 fails → lock released → 下一次启动可 acquire。  
每个阶段必须 PASS。禁止只测单一失败点。

Test 4 — Release is idempotent  
连续调用两次 release：不报错；删除后第二个进程创建的同名 lock  
不被误删（pid 校验生效）。必须 PASS。

Test 5 — Empty / corrupted lock content tolerated  
预置 node.lock 内容为空、仅 pid 字段、乱码三种情况：  
启动必须稳定返回 DATADIR_LOCKED，不得 panic，不得报 replay 错误。  
必须 PASS。

Test 6 — CLI hint present  
触发 DATADIR_LOCKED，捕获 stderr：  
必须包含固定引导文案与实际 datadir 路径；  
不得包含"自动"处理的暗示。必须 PASS。

Test 7 — Panic path releases lock（如可注入）  
通过测试 hook 在 runtime start 中注入 panic：  
最外层 defer 必须执行 release，随后进程退出；  
残留 lock 内容 pid 指向已退出进程，不得影响下一次启动的拒绝语义。  
如注入 panic 需要修改生产代码结构，必须先 STOP 报告，不得为测试开后门。
